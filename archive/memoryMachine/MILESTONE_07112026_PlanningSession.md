*2026-07-11. Snapshot of a planning-only session (no code changes yet) covering three related architecture threads. Written as Step 0 of the approved implementation plan, before any of it is built — this doc is a research snapshot, not a spec of finished work.*

## Context

Session started from two small asks — "paint shade and paint water should be different categories" and "does greenscape automatically add trees? if so, put trees in the shade portion" — while the user had the legacy diagram tool open and asked to also plan stitching its diagram-generation capability into the live app, plus a separate ask about real vector linework export from the current 3D view. ## Thread 1: `water_shade` paint category — current state

- `PaintOverlay.jsx` (lines 10-16) paints one combined boolean category, `water_shade` (`#22b8c8`), alongside `hardscape`/`greenscape`/`amenity_resting`. `ParamPanel.jsx` (lines 5-11) independently maintains a **second, separately-defined** copy of the same category list — not shared from one source, a real drift risk that's already bitten this codebase once.
- `terracing_engine.py`: `is_water_shade` is neither a hard excavation veto (like `is_hardscape`) nor an additive depth weight (like `sketch_weight`) — it has **zero influence on excavation depth**. Its only consumer is `_classify_typology()`: `if v.z_ft < 0 and v.is_water_shade: return "GROTTO"`. Un-excavated water_shade paint currently produces no classification and no visible effect at all — no ground-cap render exists for it (unlike `greenscape`'s `GreenscapeGround`).
- **Key discovery**: `circulation_network.py`'s motivator system (`DEFAULT_MOTIVATOR_WEIGHTS = {"shade": 1.0, "water": 1.0, "rest": 1.0, "foot_traffic": 1.0, "deficit": 1.0}`) already treats "shade" and "water" as **distinct concepts**, with separate UI sliders in `ParamPanel.jsx` presented as if fully independent — but derives them **asymmetrically** from the single upstream `water_shade` mask: "shade" reads `v.is_water_shade` directly (any elevation, no excavation needed — every painted cell becomes a shade attractor); "water" never reads the mask at all, only comes from already-*built* GROTTO amenity props (a strict, excavated subset) plus unrelated SANCTUARY fountains. This strongly suggests the split was anticipated in the circulation-network design but never finished upstream in the paint layer — splitting the paint category properly fixes a real latent bug (the "shade" attractor bucket has been reading the wrong/conflated mask), not just a naming cleanup.
- `TypologyAssetEngine.tree_specs()` places `tree_trunk`+`tree_canopy` pairs on every `is_greenscape` cell (thinned by a fixed `gx % 3 == 0 and gy % 3 == 0` grid spacing, no other filtering) — grass and trees currently share one boolean with zero separation.
- The live `outputs/cockpit/web_paint_state.json` on disk has real data under the old `water_shade` key (populated via `ingest_legacy_diagram.py --install-as-live` earlier this session) — any schema change here needs an explicit, safe migration, not a silent break. A real data-loss incident already happened once this session from a careless fixed-name backup during that same script's development; the fix (timestamped backup filenames) is already in place in `ingest_legacy_diagram.py`'s `install_as_live()` and should be reused, not re-invented, for this migration.

## Thread 2: the legacy diagram tool — what it actually is

Root-level `index.html` + `static/main.js` (served by `app.py`'s `GET /`) is **not** a freehand paint tool — it's an AI-prompt-driven **precedent remixer**. A user types a prompt → `ai_synthesizer.generate_spatial_seed` (Gemini/Ollama) picks real polygon layers out of a curated library of actual park plans (`data/ParkSVG/`: Pershing Square itself, Parc de la Villette, Zaryadye, Schouwburgplein, Gardens by the Bay) → composites them into an SVG via `Engine2D.render()`. A manual mode also exists (pick a precedent layer, drag X/Y/scale/rotation sliders). AI-generated 3D props (ComfyUI Flux→TripoSR GLB) can also be loaded into a Three.js preview of the real Pershing OBJ, positioned via a hand-calibrated SVG↔OBJ coordinate mapping — not fused with the real terrain mesh.

- Its diagram legend (`KNOWN_LAYERS`/`TARGET_LAYERS`) is much richer than the live app's paint categories: `BOUNDARY, GREEN_SPACE, SHADE, WATER_FEATURES, STREET, PEDESTRIAN_PATH, MAJOR_ATTRACTORS, MINOR_ATTRACTORS, UNIQUE_ELEMENTS, STREET_FURNITURE, PARKING`.
- **Real bug found this session, not previously known**: `_getLayerColor()` (`static/main.js:1073-1079`) gives `SHADE` the *exact same color* as `GREEN_SPACE` (`#4CAF50`, both matched by `id.includes('GREEN') || id.includes('SHADE')` on the same line) — so no diagram exported by this tool, ever, could visually distinguish shade from greenscape, even though the underlying `MemoryState.stack` data model correctly tracks `layerId: 'SHADE'` as its own thing. There's already a more correct, unused color sitting in `ZONE_MATERIALS.SHADE` (`0xBCAAA4`, a tan/beige) — defined for 3D material recoloring, never wired to the 2D/export legend.
- Export (`POST /api/export-diagram`, 4 modes: svg/jpg × color/grey) writes to `archive/diagrams/generated/` — 904 files exist there today. This is exactly the corpus `ingest_legacy_diagram.py` (built earlier this session) already consumes for the historical-diagram rectify+segment pipeline.
- **No JSON export of the diagram model exists anywhere** — only images. `MemoryState.stack` (the real in-memory vector representation, with known `layerId`s and transforms) is never persisted to disk in any form.
- `PaintOverlay.jsx` (the live app's actual functional design input) and the legacy tool have never shared a pipeline or data model — different coordinate representation (raster canvas vs. SVG groups+transforms), different category sets, no code path connects them today beyond `ingest_legacy_diagram.py`'s recently-built, manual-CLI-only image converter.
- `logic/diagram_agent.py`, `logic/ai_vision_tracer.py`, `logic/rhino_diagram_parser.py`, `logic/svg_remixer.py` are all real, functional CLI utilities with **zero importers anywhere** in the live app — confirmed dead code relative to what the browser actually reaches. `static/main.js`'s "Demo Mode" (Blender-headless alternative to the ComfyUI path) is also dead — it calls `POST /api/blender-demo`, a route that doesn't exist anywhere in `app.py`.

## Thread 3: vector linework export — what's reusable vs. new

- The current "Export PNG" button (`Viewport.jsx`'s `handleExport`, lines 876-886) is a pure client-side `canvas.toDataURL('image/png')` screenshot of whatever the WebGL canvas currently contains — no backend call, no vector data, and critically: **the browser's camera state (position, orbit angle, direction) has never been sent anywhere**. It just rasterizes whatever's currently on screen, including free-orbited perspective views.
- `vector_export.py` already has the hard computational-geometry piece solved: `compute_feature_edges()`/`_batch_visible()` implement real hidden-line removal (silhouette + crease edge detection, ray-cast visibility testing) via `axonometric_projection(mesh, view_dir=...)` — and this function is **already generic over an arbitrary `view_dir`**, not hardcoded internally. It's just only ever *called* with one fixed default (`AXO_VIEW_DIR`, chosen for one specific historical framing) today.
- **It has never been wired to any HTTP endpoint.** Confirmed via grep: zero references in `logic/pershing_api.py`; the only caller anywhere is `run_vector_export_demo.py`, run manually, writing output to disk (`outputs/vector_export_test/`, served read-only as static files at `/pershing-context` — but that's just serving whatever the demo script already wrote, not a live invocation path).
- `LAYER_PROJECTION` currently means **two different things** in two different existing code paths: empty/unimplemented "background geometry behind the cut plane" for the plan/section-cut paths (explicitly flagged in the module's own docstring as a known gap), vs. "the visible axo linework itself" for the axonometric demo path. Neither usage means "bucket geometry by distance from camera into depth layers" — that's genuinely new logic, not a rename of something that already exists.
- `trimesh`, `ezdxf`, and `matplotlib` are all actually imported by `vector_export.py` but **absent from `requirements.txt` entirely** — the module only works in this dev environment by coincidence of what's already installed system-wide (the project's own `.venv`/`venv` was found to be broken/misconfigured, pointing at a Python install path that doesn't exist on this machine).
- Resolution during planning: since Three.js `OrthographicCamera` supports free orbit exactly like `PerspectiveCamera` (parallel projection throughout, no vanishing point regardless of angle), scoping this feature to orthographic modes with free orbit — rather than also supporting free-orbit perspective — means "arbitrary current view direction" is *exactly* what `axonometric_projection()` already accepts as a parameter. No new projection math is needed; the real new work is camera-direction transport (frontend→backend, doesn't exist), a real endpoint (doesn't exist), and depth-band bucketing (doesn't exist).

## Where this leaves things

Full three-feature implementation plan is at `C:\Users\bletch\.claude\plans\i-want-to-modify-modular-blossom.md` (local plan file, not in the repo). Summary of decisions made during planning:

1. **Water/shade split**: rename `is_water_shade`→`is_water` (kept) + new `is_shade`; move `tree_specs()` from `is_greenscape` to `is_shade`; migrate the existing on-disk paint state via a graceful old-key fallback (not a separate script), backing up with a timestamped filename. Scoped to just this split — not expanding to the legacy tool's full richer legend this round.
2. **Diagram input**: a genuinely separate, sibling UI panel to painting (not routed through `PaintOverlay`'s UI), reusing/extending `ingest_legacy_diagram.py`'s already-calibrated rectify+segment pipeline, color-based only for now (pattern recognition explicitly deferred). Requires fixing the `SHADE`/`GREEN_SPACE` color collision first.
3. **Vector export**: scoped to orthographic + free-orbit camera modes (not free-orbit perspective), reusing `axonometric_projection()` largely as-is, adding camera-direction transport + a new endpoint + depth-band layer bucketing (a handful of near/mid/far bands, not per-object granularity) + fixing the `requirements.txt` gap.

Sequencing: Feature 1 (water/shade) must land and be verified before Feature 2 (diagram input)'s converter targets the new schema. Feature 3 (vector export) is independent and can happen in any order.
