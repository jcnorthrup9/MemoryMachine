### Feature 3 — Vector linework export (biggest arc this session, several real dead ends before landing)
Started as "wire `vector_export.py`'s existing `axonometric_projection()` to an arbitrary live camera direction." What actually happened, in order:

1. **Terrain-mesh rewrite** (`terracing_engine.py`'s new `classify_terrain_cells()`, `vector_export.py`'s new greedy-rectangle-merge + real-slab-boolean-cut machinery) — replaced "one box per voxel, unconditionally" with "real slab plates (boolean-cut with `manifold3d`) where real precedent exists, greedy-merged boxes only for genuinely new/designed terracing." Real, lasting win: 618,900 → 33,560 faces for the full combined mesh. **This did not fix the actual crash** — see next point — but it's still valuable for `vector_export.py`'s other (non-axonometric) cut/plan functions and is fully committed.
2. **Discovered the crash wasn't about face count at all.** Even at 33,560 faces, `axonometric_projection()` still failed (29 GiB allocation attempt) — a `trimesh`/`rtree` ray-triangle candidate-search pathology tied to ray-count × spatial layout (many separate column objects), not fixable by further mesh simplification. Confirmed the real culprit along the way: the Rhino column prototype mesh (1984 faces, non-watertight) instanced 294 times was 99.3% of the pre-simplification mesh — decimated to 100 faces/instance as a real, useful fix, but the deeper ray-caster issue persisted regardless.
3. **Pivoted to Blender's native Grease Pencil Line Art** instead of continuing to fight `trimesh`'s pure-Python ray-caster. This mechanism already existed in the repo (`blender/pershing_headless_build.py`'s `build_line_art()`, wired to `POST /api/pershing/blender-build?lineart=true`) but deliberately excluded real columns/slabs (to avoid double-rendering what the live viewport already shows separately) and had a hardcoded camera direction.
4. Extended it: real columns/slabs as lightweight native Blender primitives (not the heavy Rhino OBJ — same lesson from point 2, applied on the Blender side too), `--view-dir` camera-direction parameterization, depth-band SVG layering (`near`/`mid`/`far` `<g>` groups, computed from camera-space Z during the same projection pass the SVG writer already does). Frontend: `Viewport.jsx`'s "Export Current View" button (renamed from "Export PNG") now also derives the live orbited camera direction and triggers this pipeline, auto-downloading the resulting SVG.
5. **Two more real bugs found only by testing through an actual browser** (Playwright), not just direct HTTP calls:
   - An `argparse` gotcha: a camera direction with a negative first component (e.g. `-0.2,-0.98,0.09`) made `subprocess.run`'s two-token `["--view-dir", value]` form get misparsed as "no value given" — fixed by switching to the single-token `--view-dir=value` form.
   - A **systemic, pre-existing bug**, unrelated to this session's new code: `vite.config.js`'s dev-server proxy only ever covered `/api` and `/pershing-sketch` — every other backend static mount (`/blender-headless-output`, `/pershing-context`, `/comfy-output`, `/models`, `/static`, `/archive`, and this session's new `/legacy-diagrams`) was never proxied. The pre-existing `BlenderBuild.jsx`/`LineArtOverlay.jsx`/`StaticContext.jsx` worked around this by each hardcoding an absolute `http://127.0.0.1:8000` URL — which was **already stale** (backend has been on :8001 all session due to the port-8000 phantom listener) and had been silently broken the whole time, just never exercised in a way that surfaced it. Fixed properly: extended the proxy to cover every static mount, removed all three hardcoded/duplicated host constants.

Final verification was a real Playwright-driven browser test: loaded the app, clicked an orthographic view preset, dragged the mouse to orbit the camera, clicked "Export Current View," confirmed both a PNG and a real depth-layered SVG (2870 strokes, correct near/mid/far grouping) downloaded automatically — then plotted the actual downloaded SVG with matplotlib and visually confirmed it's a real, correctly-oriented isometric line drawing of the site.

## What's NOT done / open items for next session

1. **Port 8000's phantom listener** — never resolved this session (or the one before it). `vite.config.js`'s proxy still points at `:8001` with a comment explaining why. Try a reboot; if that clears it, revert the proxy target back to `:8000` and remove the explanatory comments in `vite.config.js`, `LineArtOverlay.jsx`, `BlenderBuild.jsx`, `StaticContext.jsx`.
2. **The "water" motivator asymmetry** (flagged in `CURRENT_STATE_07122026.md`) — "shade" now reads its mask directly, "water" still only comes from built GROTTO/fountain props. Not fixed, just documented. A `circulation_network.py` change (add a direct `is_water` → "water" bucket in `sample_attraction_points()`) would resolve it if wanted.
3. **Tan/shade color threshold in `ingest_legacy_diagram.py`** (`SHADE_TAN_RGB`) is arithmetically derived from `ZONE_MATERIALS.SHADE`, not empirically verified — no diagram existed with a real tan pixel until this session's `_getLayerColor()` fix. Generate a fresh diagram via the legacy tool with an actual SHADE-layer pick, export it, sample the real pixel color, and confirm/adjust the threshold before trusting Diagram Input's shade detection in production.
4. **`vector_export.py`'s standalone DXF/SVG/PNG path is still not wired to any live endpoint.** The terrain-mesh rewrite (this session) makes it faster/lighter, but `run_vector_export_demo.py` remains a manual script. If real DXF output (not just SVG) is ever wanted from the live app, that's separate work — the Blender pipeline built this session only produces SVG.
5. **`blender_cockpit.py`'s `build_terrace_mesh()`** was explicitly left as box-per-voxel (not given the same real-slab-boolean treatment as `vector_export.py`) — flagged as a natural follow-up, since Blender has real native boolean tools (`bpy`) that would likely be an even better fit there than porting the trimesh approach.
6. **Gray catchall collision** in `_getLayerColor()` (`PEDESTRIAN_PATH`/`STREET`/`BOUNDARY`/`PARKING` all map to the same gray) — accepted as "hardscape catches everything else" for this round, not revisited.
7. Real bug-hunting pattern worth remembering: **this session's two most consequential bugs (argparse, Vite proxy) were only found by testing through an actual browser**, not by direct HTTP/Python calls, even though those also "passed." If a feature touches the frontend at all, a real Playwright click-through before declaring it done is worth the time — it already caught two genuine, unrelated regressions this session alone.
